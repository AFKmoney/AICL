   200→| Component | Purpose |
   201→|-----------|---------|
   202→| **PatternLearner** | Extracts verbs/objects from unmatched actions, classifies into 16+ categories, generates templates |
   203→| **SpecEvolver** | Fixes verification failures, test failures, and audit gaps automatically |
   204→| **TestRunner** | Runs pytest, parses output, analyzes failure patterns (imports, attributes, types, assertions) |
   205→| **LoopController** | Manages convergence detection, max iterations, composite scoring |
   206→| **AutonomousCompiler** | Orchestrates the full loop with `evolve()` method |
   207→
   208→### Pattern Learning
   209→
   210→The PatternLearner extracts new behavior patterns from unmatched action descriptions:
   211→
   212→- **Verb extraction**: 40+ action verbs (create, update, validate, compute, transform, store, load, encrypt, connect, notify, etc.)
   213→- **Object extraction**: Domain-specific objects (account, transaction, card, loan, user, message, request)
   214→- **Category classification**: 16+ categories (CREATION, UPDATE, VALIDATE, ROUTE, COMPUTE, TRANSFORM, STORE, LOAD, ENCRYPT, CONNECT, NOTIFY, FINANCIAL, SECURITY, AUDIT, etc.)
   215→- **Template generation**: Per-category code templates
   216→- **Confidence tracking**: Learned patterns start at 0.7 (vs deterministic 0.95), distinguishing learned from built-in
   217→
   218→### Specification Evolution
   219→
   220→The SpecEvolver automatically fixes AICL specifications based on three types of feedback:
   221→
   222→1. **Verification failures**: Missing risk/recovery pairs, missing actions, incomplete specifications
   223→2. **Test failures**: Missing imports, attributes, definitions, type signatures
   224→3. **Audit gaps**: Coverage below 1.0, orphan artifacts
   225→
   226→All spec changes are tracked with `ProvenanceType.SPEC_EVOLVED`, maintaining the provenance chain even as the specification itself evolves.
   227→
   228→```bash
   229→aicl evolve banking.aicl --max-iterations 10
   230→aicl evolve banking.aicl --watch  # continuous mode
   231→```

   235→## AI-Powered Self-Writing Compilation
   236→
   237→The **SelfWritingCompiler** is the highest level of the AICL system. Given any task description, it can:
   238→
   239→1. Generate a complete AICL specification from scratch
   240→2. Compile it through the autonomous loop
   241→3. AI-diagnose any failures
   242→4. AI-fix the specification
   243→5. Iterate until convergence
   244→
   245→### The Self-Writing Loop
   246→
   247→```
   248→DESCRIBE → AI-GENERATE → COMPILE → VERIFY → TEST →
   249→AI-DIAGNOSE → AI-FIX → RECOMPILE → ... → CONVERGE
   250→```
   251→
   252→If AI is not available, the system gracefully degrades to the deterministic autonomous loop (PatternLearner + SpecEvolver).

   470→
   471→| Level | Name | Keywords | Purpose |
   472→|-------|------|----------|---------|
   473→| 1 | Architecture | `Goal`, `Layer`, `Validation`, `Risk`, `Recovery` | System structure + risk management |

   479→| 7 | Optimization | `Optimize`, `Priority` | Performance targets |
   480→| 8 | Learning | `Learn`, `Adapt` | Adaptive behavior |
   481→| 9 | Security | `Encrypt`, `Protect` | Security requirements |
   482→| 10 | Native Code | `Native` | Inline code in other languages |

   544→### Deterministic Behavior Compilation
   545→
   546→The **Behavior Pattern Library** maps action descriptions to concrete code through 30+ deterministic patterns:
   547→
   548→| Category | Patterns | Example |
   549→|----------|----------|---------|
   550→| Movement | MOVE, MOVE_BALL, REFLECT_VELOCITY, CLAMP_POSITION | "Update paddle position" → MOVE pattern |
   551→| Creation | CREATE, INIT_LAYER, CREATE_WINDOW | "Create new game" → CREATE pattern |
   552→| Communication | BROADCAST, SEND_MESSAGE | "Transmit message" → BROADCAST pattern |
   553→| Update | UPDATE, INCREMENT_SCORE, UPDATE_STATE | "Clamp ball position" → CLAMP pattern |
   554→| Display | DISPLAY, RENDER_FRAME, HIGHLIGHT | "Draw game frame" → RENDER pattern |
   555→| Validation | VALIDATE, CHECK_COLLISION | "Validate move" → VALIDATE pattern |
   556→| Networking | CONNECT, RECONNECT, DISCONNECT | "Connect to server" → CONNECT pattern |
   557→| Persistence | STORE, LOAD | "Save game state" → STORE pattern |
   558→| Security | ENCRYPT_DATA, PROTECT_ACCESS | "Encrypt message" → ENCRYPT pattern |
   559→| Sync | SYNC_STATE, BUFFER_INPUT | "Sync state" → SYNC pattern |
   560→| Game | END_GAME, APPLY_PHYSICS | "End game" → END_GAME pattern |
   561→| Adaptation | ADAPT_QUALITY, SUGGEST, QUEUE_MESSAGE | "Adapt quality" → ADAPT pattern |
   562→
   563→When no pattern matches, the **sub-language parser** handles explicit action specifications:
   564→
   565→```aicl
   566→Behavior MovePaddle
   567→    Input: Player direction string
   568→    Action: assign paddle_position += direction * speed
   569→            clamp paddle_position between 0 and screen_width
   570→```
   571→
   572→When even the sub-language can't help, the **PatternLearner** extracts the action's verb and object, classifies it into a category, and generates a learned template at confidence 0.7 (vs deterministic 0.95).
   573→
   574→This means **zero TODOs** in compiled output. Every behavior compiles to real, executable code — and every compilation decision is recorded in the provenance chain.

   741→### The Conceptual Trajectory
   742→
   743→The roadmap reflects a deepening understanding of what auditable compilation means:
   744→
   745→```
   746→v0.1–v0.3:  "I want a simpler language than C++"
   747→v0.4–v0.5:  "I want the compiler to explain itself"     → Explicable Compilation
   748→v0.5–v0.6:  "I want to measure that explanation"         → Auditable Compilation
   749→v0.7:        "I want proof that doesn't require trust"    → Proof of Origin + Independent Verification
   750→v0.8:        "This idea transcends AICL itself"           → The No-Orphan Property (Position Paper)
   751→v0.9:        "I want to verify the specification"         → Specification Compilation
   752→v0.10:       "I want multi-file programs"                 → Module System + Cross-File Provenance
   753→v0.11:       "I want the proof to be tamper-proof"        → Cryptographic Proof Signing
   754→v1.0:        "I want it in other languages"               → Multi-Language Targets
   755→v1.5:        "I want to see the provenance"               → Provenance Visualization
   756→v2.0:        "I want self-healing at runtime"             → Self-Healing Runtime
   757→v2.5:        "I want safe memory management"              → Ownership Model
   758→v3.0:        "I want the architecture to improve itself"  → Autonomous Optimization
   759→v3.5:        "I want the code to write and validate itself" → Autonomous Compilation Loop
   760→v4.0:        "I want it to code itself for any task"      → AI Self-Writing Compiler
   761→```
   762→
   763→Each stage discovered that the previous stage's endpoint was actually the beginning of a deeper problem. Explicable compilation raised the question of measurement. Measurement raised the question of trust. Trust raised the question of independent verification. Verification raised the question of specification quality. Specification raised the question of multi-file programs. Multi-file raised the question of proof integrity. Proof integrity raised the question of language independence. Language independence raised the question of visibility. Visibility raised the question of runtime behavior. Runtime raised the question of memory safety. Memory safety raised the question of architectural evolution. Evolution raised the question of autonomous compilation. Autonomous compilation raised the question of self-writing code. And self-writing code raises the question: can a compiler that writes itself still prove where every line came from? AICL's answer is yes — because provenance is not an afterthought, it is the architecture.
